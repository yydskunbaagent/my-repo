## 1.2 v0.2 的架构漏洞（外部评审指出，已采纳）

| 漏洞 | 后果 | 修正 |
|---|---|---|
| 授权语义分裂：一边说"对齐官方 Grant"，一边自建 CIDR/端口/时间窗 | 运维和审计要面对两套授权结构 | 统一为 **Grant Envelope**（§4） |
| nftables 按"开测时解析的 IP"写死五元组 | **CDN 轮询 IP 会被静默丢弃**；302 跳到边缘节点直接失败 | 改为 DNS 感知的动态集合 + 受控解析器（§5.1） |
| 把"脚本执行拦截"当核心门禁 | base64/动态拼接可绕，Python 层正则挡不住 | 扫描节点**不装通用 shell**；hook 降级为纵深（§6.1） |
| 黑盒机械套用"正/负对照 + 清理完成" | 只读探测没有清理动作，大量结果被迫卡在 NOT_RUN | 拆成两条证据通道（§6.3） |
| §9 花力气验 Windows 兼容 | nftables / `nmap -sS` / 原始套接字全依赖 Linux 内核 | 服务端锁 Linux，Windows 只作终端入口（§9） |

**评审里我不采纳的一条**：它建议把自研的 CIDR 授权"收口进官方的 `mint_grant`"。这在工程上做不到——`mint_grant` 是 `hermes_security` 包内的函数，绑定它自己的 SQLite store 与 scan 生命周期，"收口"等于 fork 官方插件，与"不自研白盒"的原则直接冲突。正确做法是**统一信封形状与命名，物理存储分离**，报告层合并呈现（§4）。

## 2. 事实基线（已逐条核实）

### 2.1 底座 `hermes-agent`
- 263,181 star，2025-07 建仓，2026-11-13 仍有推送
- 迭代预算：父默认 **500**、子 `delegation.max_iterations` 默认 **250**（`agent/iteration_budget.py` docstring 写 50，与配置示例不一致，以 config 为准）
- 并行：单批 `_MAX_TOOL_WORKERS=8`；子 Agent 并发 `max_concurrent_children=10`；委派深度 1–3
- 工具：`register()` 实际调用 **78 处**；审批子系统 11 文件 / 5,286 行（含 1,929 行命令去混淆识别）
- 扩展点：**plugin hook**（`ctx.register_hook`）与 **gateway hook**（`~/.hermes/hooks/`）是两套，`pre_tool_call` 只属于前者
- `pre_tool_call` 契约：返回 `block`/`approve`/`modify`，优先级 `block > approve > 无`；超时（默认 30s）或抛异常 **fail closed**
- 安全边界（`SECURITY.md` §2.2 原文）：进程内一切组件都不构成隔离，唯一边界是操作系统
- 已知漏洞：`CVE-2026-71963`（RCE，0.18.2–0.21.0，修于 `f6234d0`）、`CVE-2026-85105`（`_sess_nowait`）

### 2.2 官方插件 `hermes-security`（v0.1.3，requires Hermes ≥0.21.5）
- 9 个工具：`security_scan_start/get/checkpoint/submit_worker_result/record_validations/record_chains/finalize/cancel/export`
- hooks：`on_session_end`、`subagent_start`、`subagent_stop`（**没有 `pre_tool_call`**）
- 模式：`--mode standard|deep|diff`，另有 `--tests`、可续跑、固定预算
- 产物：findings / candidates / coverage / scan-manifest / chains，导出 MD/JSON/CSV/**SARIF**
- 方法论（`references/`）：boundary-before-claim、可达性、反证、actor×resource×operation、OWASP Top10:2025 + ASVS 5.0.0 车道
- **授权模型**（`references/validation-policy.md`）：
  - 静态为默认；静态 receipt 对运行时校验一律记 `NOT_RUN`
  - `active-authorized` 必须由用户执行 `/security authorize-validation <scan> <origin>`；**Agent 可以提议，永远不能自铸授权**
  - grant 绑定：scan + 规范化 scheme/host/port **origin** + 允许动作 + 有效期 + 请求预算
  - **字面 IP 需要单独授权**；域名授权不隐含其解析到的 IP
  - 运行时计划必须带正/负对照（positive/negative control）+ 清理策略，只允许 argv，禁止 shell 字符串
  - 本地执行限制：一次性副本、拒绝逃逸软链、拒绝 shell 与网络工具、CPU/1GiB/64MiB/超时/进程组终止

## 4. 对齐官方授权模型（关键设计决策）

不重造 grant 概念，直接沿用 `hermes-security` 的五条原则，这样两套东西的语义一致，运营和审计不用学两套：

| 官方原则 | 在本项目中的落法 |
|---|---|
| Agent 可提议，不可自铸授权 | `scope.yaml` 列入 `protected_paths`，`write_file`/`patch` 命中即拒；gate 只读不写 |
| 授权绑定 origin + 动作 + 有效期 + 预算 | `targets`（域名/IP/CIDR + 端口）× `allowed_actions` × `window` × `rate_limit` |
| 字面 IP 需单独授权 | 保留：CIDR 与 IP 必须显式列出 |
| 域名授权不隐含解析到的 IP | **采纳并加固**：域名在范围内时，若解析结果落在私网/链路本地/保留段，则阻断，除非该 IP 被显式授权 |
| 结论必须有正/负对照才可称"确认" | 黑盒侧拆两条证据通道（§6.3），只有主动 PoC 需要对照 |

### 4.1 Grant Envelope（统一信封，替代两套语义）

**只保留一种授权结构**，`kind` 区分粒度，校验器与审计记录形状完全一致：

```yaml
grants:
  - id: G-001
    kind: netrange            # netrange | origin
    value: 10.20.30.0/28      # netrange 用 CIDR；origin 用 scheme://host:port
    actions: [recon_active, vuln_scan]
    ports: [80, 443, 8080]    # origin 粒度时由 value 自带，此处为空
    window: {start: ..., end: ...}
    budget: {rps_per_host: 5, total: 20000}
    minted_by: user           # 只有 user 能写入；agent 只能读
  - id: G-002
    kind: origin
    value: https://app.example.com:443
    actions: [exploit_proof]  # 需要人工确认的动作单独成 grant
    minted_by: user
```

三条约束：

1. **单一校验入口**：`validate(envelope, request)` 一处实现，两种 kind 走同一状态机，审计记录只写 `grant_id`。
2. **agent 不可写**：信封文件进 `protected_paths`，`write_file`/`patch` 命中即拒。
3. **物理存储分离、形状对齐**：官方 `hermes-security` 的 grant 存在它自己的 SQLite（`mint_grant` 绑定 scan 生命周期），我们的存在 `grants.yaml`。**不强求合并**，但 `grant_id` 命名、字段名、审计字段保持一致，报告层按 `grant_id` 合并展示。

## 5. 架构：三道防线，只有一道算边界

| 层 | 机制 | 能拦什么 | 拦不住 |
|---|---|---|---|
| **OS / 网络** | 扫描节点独立网段 + nftables 五元组放行 | 一切越界出网 | 允许范围内的滥用 |
| **Plugin hook** | `pre_tool_call`（block/approve/modify） | 命令级目标越界、脚本执行、云元数据、限速 | 目标藏在脚本内部、编码绕过 |
| **Skill** | `web-pentest` 流程约束 | 行为引导 | 被注入后可绕过 |

依据是官方自己的定性：`SECURITY.md` §2.2 —— 进程内没有隔离，唯一边界是 OS。

### 5.1 网络拓扑（必须绕开的坑）

官方 egress 方案（`docs/user-guide/egress/network-isolation.md`）是 `internal: true` 网络 + squid `CONNECT` 白名单，**只承载 HTTP/HTTPS**：

- `nuclei` / `httpx` / `ffuf` → 可用
- `nmap -sS`、masscan、UDP、裸 TCP → 代理协议不支持，且 `internal` 网络无默认路由，**直接失败**
- 失败表现为"目标不可达"，极易误判为靶场问题

因此：

```
┌─ 推理节点（internal，无出网）────────┐
│ Hermes + hermes-security + 模型 API  │  出口仅放行模型 API 域名
│ 工具调用 → JSON 任务 → 扫描节点       │
└───────────────┬─────────────────────┘
                │ 只传结构化任务/结果
┌───────────────▼─────────────────────┐
│ 扫描节点（一次性 VM / 容器）          │
│ nftables: 默认 drop                  │
│   allow → scope CIDR × scope 端口    │
│ 无模型 Key / 无宿主凭据 / 用完即毁     │
└─────────────────────────────────────┘
```

要点：扫描节点**不持有模型凭据**，被打穿也拿不到账号池；裸 TCP 走 nftables 而非代理；任务与结果只走 JSON 文件/RPC，不共享 shell。

**不使用** `docker_egress.py` 的 iron-proxy（它是为防凭据外泄设计的，方向相反）。

### 5.2 五元组不能写死（CDN 场景会静默丢弃）

按"开测时解析到的 IP"生成静态 nftables 规则是错的：目标挂 CDN 时 IP 每次解析都可能变，302 跳到边缘节点也会换 IP，结果就是**扫描流量被内核静默丢弃**，表现为随机超时，极难排查。

正确做法分两类目标：

| 目标类型 | nftables 策略 |
|---|---|
| `netrange`（IP/CIDR） | 静态集合，直接 `allow ip daddr @scope_v4`，无歧义 |
| `origin`（域名） | **DNS 感知的动态集合**：强制所有出站 53 只通向受控解析器；该解析器仅对本 scope 内域名应答，并在每次应答时把 IP 写入带 TTL 的 nftables set；80/443 只放行到该 set |

配套要求：

- **必须放行受控 DNS（UDP/TCP 53）**，否则域名类目标全部不可用——这是上一版漏掉的硬依赖
- 解析器对 scope 外域名返回 `REFUSED`，防止借 DNS 做外送隧道
- 直连任意 IP 一律 drop，杜绝绕过解析器
- 302 跳转到 scope 外域名时，新解析被拒绝 → 自然阻断，符合预期

### 5.3 扫描节点不得装通用 shell

推理节点若被注入，虽拿不到扫描节点的出网权限，仍可能通过 MCP/SSH 传恶意参数：比如利用扫描器的文件读写参数读配置、往临时目录写脚本再执行。因此：

- 扫描节点**不提供 terminal / 通用 shell**，只暴露**参数强类型校验的原子工具**（`scan_nmap(target, ports, flags_whitelist)` 这类）
- 工具参数先过 JSON Schema 校验，flag 走白名单，拒绝自由拼接
- 官方 `mcp-serve` 插件默认就屏蔽终端与文件工具，可直接复用其接口暴露方式

这条替代了"在 `pre_tool_call` 里解析 shell 命令"的思路——后者靠正则挡不住 `base64 -d | sh`、变量替换、Python 动态拼 URL。

## 6. 自研部分的设计要点

### 6.1 `scope-gate` 插件（已实现骨架，`build/scope_gate/`）

**定位先说清**：门禁管的是**推理节点的工具调用**（模型决定"打哪"的那一刻）。扫描节点不靠它——那边靠"无通用 shell + 原子工具 + nftables"三件套。hook 是纵深防御的一层，不是边界，这一条与 `SECURITY.md` §2.2 一致。

- 形态：**plugin**（`plugin.yaml` + `__init__.py:register(ctx)`），不是 `~/.hermes/hooks/`（那是 gateway hook）
- 判定顺序固定：grant 可用性 → forbidden → 时间窗 → 动作白名单 → 目标解析 → 云元数据/排除项/范围/端口 → 限速 → exploit 升级人工
- 目标归一化覆盖：整数 IP、十六进制、八进制、短写、userinfo、尾点、IPv6、IDN
- 脚本执行在**推理节点**一律拒（`bash scan.sh` 看不到真实目标）；扫描节点则根本不提供 shell
- 限速：令牌桶 + 累计双约束，SQLite 持久化，重启不清零
- 审计：哈希链 JSONL，可 `verify_chain()` 定位篡改点
- **待改（骨架尚未实现）**：域名解析到私网/链路本地/保留段时，除非该 IP 显式在 grant 内，否则阻断。当前引擎只校验解析结果是否命中排除项，强度不够
- **待改（骨架尚未实现）**：`scope.yaml` → `grants.yaml` 的信封结构（§4.1），校验器合并两种 kind

### 6.2 必须加的负向测试（P1 出口）
整数 IP `2130706433`、八进制 `0177.0.0.1`、短写 `127.1`、`user@host`、`bash scan.sh`、3xx 跳外域、`169.254.169.254`、域名解析到 `10.x`、grant 文件损坏、审计写盘失败、限速状态丢失——**全部必须拒绝**。

### 6.3 两条证据通道（不能一刀切）

官方要求"正/负对照 + 清理完成"才可称 `passed`，这在白盒可控副本里成立，但在黑盒只读探测上没有"清理动作"，硬套会让绝大多数结果卡在 `NOT_RUN`。因此拆两条：

| 通道 | 适用 | 证据门槛 | 可达到的最高结论 |
|---|---|---|---|
| **被动观察** | 指纹、banner、响应头、公开路径探测 | 至少两路独立特征交叉印证（如版本串 + 已知行为），不触碰状态 | `observed`（不得称 confirmed） |
| **主动 PoC** | 需发包验证的漏洞 | 正对照（标记出现）+ 负对照（良性输入/修复后，标记不出现）+ 清理完成 | `confirmed` |

报告里三档终态：`confirmed` / `observed` / `rejected`。**被动观察永远不能升到 `confirmed`**，这是防"看起来像漏洞"的关键约束。

## 7. 分期与验收

| 期 | 内容 | 出口标准（可测） |
|---|---|---|
| **P0 底座** | Hermes ≥0.21.5（跨过 CVE 区间）+ 装 `hermes-security`、`snyk`、`semgrep` MCP | `hermes plugins list` 三项 enabled；对一个开源仓库跑通 standard 扫描并导出 SARIF |

## 9. 待验证（不许当结论用）

**已决策（不再作为待验证项）**：服务端全量锁 Linux。`nftables`、`nmap -sS` 原始套接字、`unshare -rn` 都强依赖 Linux 内核，Windows 上兼容扫描后端是伪需求。Windows 只作为**终端入口**（CLI / Desktop / VS Code Remote / ACP 连到 Linux 节点）。注：官方 `hermes-security` 自带 `_win32.py`，说明上游支持 Windows，但那是给"单机审代码"用的，不适用于本项目"隔离扫描"的形态。

1. `delegate_task` 子 Agent 与 `hermes-security` 的 `subagent_*` hook 交互：官方插件靠这三个 hook 派活，若 profile 路由下不触发会**静默降级**（不报错，只是不再并发）
2. `execute_code` 单轮 RPC 内的限速计数是否与 `pre_tool_call` 共享（不共享即可批量绕过限速）
3. 跨 profile 委派时加载哪个 hooks 目录
4. `approvals.deny` 的 glob 能否匹配 wrapper 脚本内部命令（预期：不能，故选 §5.3 的"无 shell"方案而不是靠它）
5. 受控 DNS 解析器 + nftables 动态集合的实际延迟：CDN 场景下 TTL 到期与集合更新之间是否存在可被利用的窗口
6. `mcp-serve` 插件暴露 Hermes 为 MCP Server 时，默认屏蔽终端/文件工具的确切范围（已看文档，未实测）
